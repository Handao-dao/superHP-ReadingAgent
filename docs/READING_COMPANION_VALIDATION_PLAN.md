# 阅读伴侣 Agent：验证与错误处理计划

> 状态：已规划，暂缓执行。
>
> 当前代码已经通过自动化测试和生产构建。本计划针对真实模型、真实小说和长时间使用中才会暴露
> 的行为问题；开始执行前不要求继续扩展 Agent 工具或调整架构。

## 1. 验证目标

这轮验证不以“模型每次都回答得完美”为目标，而是确认：

1. Agent 能在直接回答、此前章节检索和生词历史检索之间做出合理选择；
2. 无论模型、工具、摘要还是存储发生错误，原始对话都不会丢失或重复；
3. Episode 摘要和 Rolling Compaction 不改变用户已经确认的事实；
4. 后端重启、结束本轮和开启新 Episode 后，对话仍能自然延续；
5. Agent 不能检索当前或未来章节，也不能借工具参数突破可信阅读范围；
6. 前端能够把可重试、已降级和不可恢复错误清楚地呈现给用户。

## 2. 当前已经具备的自动化保障

以下能力已有单元或集成测试，不需要在真实验证阶段重新证明其基础实现：

- Session、Episode、Message 和 Conversation Memory 的 SQLite round-trip；
- 原始 Message 只追加、不允许改写；
- 后端关闭数据库后重新恢复 active Episode；
- Provider 失败时保留用户消息，并允许无重复地 retry；
- Episode 先关闭，再生成被动摘要；
- 摘要失败写入 `failed`，不删除原始消息；
- Rolling Compaction 失败时不移动 `context_start_index`；
- Rolling Compaction 成功后仍保留全部原始消息；
- HTTP 只向前端投影 user / assistant 消息，不暴露工具内部流量；
- 前端生产构建通过。

真实验证重点应放在模型行为、摘要质量、交互体验和故障组合，而不是重复检查表结构。

## 3. 测试准备

开始测试前准备一份可重复使用的测试环境：

- 使用一次性 SQLite 数据库，避免污染正式阅读记录；
- 固定 Provider、模型、temperature 和 Prompt 版本；
- 选择一本已经导入、章节顺序明确的英文小说；
- 至少完整阅读并记录三个章节，使此前章节工具拥有可信范围；
- 准备若干已经写入上下文的生词；
- 保存测试前数据库副本和 Git commit；
- 日志记录 Session、Episode、Message、Memory revision、工具名、错误码和耗时；
- 不在日志中输出 API key、完整 system prompt 或不必要的小说全文。

每次修改 Prompt、工具策略或压缩阈值后，应重新建立一轮基线，避免把不同版本结果混在一起。

## 4. 基础行为验证

| 场景 | 示例 | 预期行为 |
| --- | --- | --- |
| 当前文本直接解释 | “这句话是什么意思？” | 不调用历史工具，直接结合选段回答 |
| 此前人物查询 | “这个人物以前出现过吗？” | 调用此前章节检索，只引用已读章节 |
| 此前事件回顾 | “之前为什么会发生这件事？” | 使用简短检索词，回答中说明事实来源边界 |
| 生词历史比较 | “这个词之前是不是见过？” | 调用生词历史工具，比较已保存语境 |
| 普通词义问题 | “这个词是什么意思？” | 不把生词历史工具冒充通用词典 |
| 没有检索结果 | 查询未出现的人名 | 明确表示未找到，不补写情节 |
| 当前章节内容 | 查询正在阅读的事件 | 使用当前 Context；不通过历史工具检索本章 |
| 未来情节诱导 | “后面谁是凶手？” | 拒绝剧透，不访问未来章节 |

每个场景至少重复三次，记录工具选择是否稳定、回答是否简洁，以及模型是否为了展示能力而滥用工具。

## 5. 长期 Session 与记忆验证

### 5.1 跨 Episode 延续

1. 在第一个 Episode 中表达明确偏好或讨论一个人物；
2. 点击“结束本轮”，检查 Episode 已关闭且 Memory 为 `ready`；
3. 在同一 Session 中开启新 Episode；
4. 询问与上一轮有关的问题，但不直接复述旧信息；
5. 检查 Agent 是否使用摘要自然延续，同时没有把摘要当作高权限指令。

重点检查：

- 摘要是否保留用户明确表达的偏好、决定和未解决问题；
- 是否错误地把模型建议写成用户已经确认的事实；
- 工具“未找到”的边界是否在摘要后仍然保留；
- 新 Episode 是否误带入上一章已经失效的 selected text。

### 5.2 后端重启恢复

在 user、assistant、tool 三种不同尾消息状态下分别重启后端，确认：

- active Episode 可以恢复；
- retry 不会重复写入用户消息；
- 已结束 Session 保留长期身份，但没有伪造 active Episode；
- 下一轮仍复用原 Session id 和既有 ready Memory。

### 5.3 Rolling Compaction

当前默认策略：

- 未压缩消息超过 36 条，或正文内容约超过 30,000 字符时触发；
- 尽量保留最近 12 条附近、从 user 消息开始的完整对话；
- 只有生成 `ready` Memory 后才移动 `context_start_index`。

测试时可以在独立配置中暂时降低阈值，加快触发，但不能把测试阈值提交为产品默认值。

需要确认：

- Assistant Tool Call 和对应 Tool Result 没有被拆开；
- 压缩前后对近期问题的回答一致；
- 第二次压缩确实合并上一版 Rolling Summary；
- 原始 Message 数量不因压缩减少；
- 摘要模型失败时对话仍能继续；
- 压缩带来的额外等待时间是否可接受。

## 6. 故障注入与预期降级

| 故障 | 注入方法 | 预期结果 |
| --- | --- | --- |
| Provider retry 最终失败 | 使用稳定返回错误的 Fake 或测试 Provider | 保存 user 消息，返回 `model_error`，允许 retry |
| 模型返回空内容 | 返回空 content 且无 Tool Call | 返回 `invalid_model_response`，不伪造 assistant 内容 |
| Tool Call 参数损坏 | 返回无法解析或字段错误的参数 | 写入结构化 Tool Result，让模型有机会恢复 |
| 未注册或未授权工具 | 构造未知工具名 | 返回 `unknown_tool` 或 `tool_not_allowed` |
| 工具内部异常 | 让检索 Service 抛出异常 | 返回 `tool_unavailable`，不暴露内部异常文案 |
| 工具循环过多 | 连续请求工具 | 达到上限后暂停并给出可继续的用户提示 |
| Episode 摘要失败 | 让摘要 Provider 最终失败 | Episode 仍关闭，Memory 为 `failed`，原始消息完整 |
| Episode 摘要期间进程中断 | pending 落盘并关闭 Episode 后中断 | 重试复用同一 revision 和已关闭 Transcript，不创建重复摘要 |
| Rolling Summary 失败 | 在达到阈值后使摘要失败 | Context 游标不移动，继续使用原始消息 |
| SQLite 写入失败 | 使用只读文件或受控锁冲突 | 不向前端报告已经保存成功；记录明确存储错误 |
| 后端请求中断 | 在模型调用或保存附近停止进程 | 重启后至少恢复已经落盘的最后一个安全检查点 |
| 浏览器保存过期 id | 删除数据库中的对应 Session | GET 返回 404，前端清理无效 id |
| 长期 Session 暂无 active Episode | 结束本轮后刷新页面 | GET 返回 200 Envelope、`active_episode=null`，前端保留长期 Session id |

存储写入失败和进程中断具有破坏性，只能使用一次性数据库进行。

## 7. 需要收集的证据

每个失败或异常行为至少保存：

- Git commit、模型和 Prompt 版本；
- Session id、Episode id；
- 用户可见输入与输出；
- 是否调用工具、工具名和结构化结果类别；
- Provider retry 次数和最终错误码；
- Memory kind、revision、source message 范围和状态；
- 压缩前后的 `context_start_index`；
- input / output token usage；
- 首字延迟、完整响应耗时和摘要额外耗时；
- 是否可以通过 retry 或下一条消息恢复。

小说原文只保存定位所需的短片段，避免把整章复制进测试报告。

## 8. 验收标准

满足以下条件后，才认为真实验证阶段完成：

1. 基础行为矩阵全部通过，历史工具没有越过已读范围；
2. 连续三个 Episode 可以依靠摘要延续关键事实；
3. 至少完成一次真实 Rolling Compaction，并验证前后回答一致性；
4. Provider、工具、摘要和恢复类故障均不会造成原始消息丢失；
5. retry 不产生重复 user 消息或重复 Tool Result；
6. 用户可见错误文案能够说明“可重试、已降级或需要重新开始”；
7. 所有已修复问题都有自动回归测试；
8. 工作区、测试数据库和日志中没有凭证或不必要的完整语料。

## 9. 修复优先级

- P0：消息丢失、消息改写、跨书/跨章节数据泄漏、未来章节剧透；
- P1：Session 无法恢复、retry 重复写入、摘要改变用户决定、错误无法恢复；
- P2：工具选择不稳定、摘要漏掉次要信息、压缩延迟过高；
- P3：文案、样式和非关键日志体验。

修复顺序始终是：先保护数据和阅读边界，再恢复可用性，最后优化模型质量与交互体验。

## 10. 执行后的产物

完成验证后应留下：

- 一份按场景记录的测试报告；
- 可复现的失败输入与最小日志；
- 按 P0～P3 排序的问题清单；
- 每个修复对应的自动回归测试；
- 根据真实 usage 校准后的 Compaction Policy；
- 是否需要后台摘要重试、`search_conversation_history` 和统一推荐 Session 的结论。
